# Development

How to build the core, run the simulations and use the tools. Run everything from the
repository root in a POSIX shell (Git Bash works on Windows). Docker is needed for Quartus,
the firmware toolchain and Verilator; Python 3 for the scripts.

## Build

```sh
tools/fw.sh          # firmware: build/firmware/firmware.bin and program.bin
tools/build.sh       # Quartus: core/output/bitstream.rbf_r
tools/package.sh     # SD card layout in build/sdcard/, copy its contents to the card's root
tools/deploy.sh /i   # package and copy to the SD card mounted at /i (or I:)
```

Quartus Prime Lite 18.1.1 runs in the image `raetro/quartus:pocket`, the version of Analogue's
core template. `tools/build.sh` ends with three summary lines (`tools/buildsum.py`): the
time and the resource use, the smallest slack of every timing check, and the logic of every
unit, each with the change against the previous build. The full log is `build/quartus.log`.
The Pocket needs the bitstream bit-reversed, `tools/reverse_rbf.py` does that.

The firmware is built by GCC 14 and picolibc from Debian trixie in Docker
(`firmware/docker/Dockerfile`); `tools/fw.sh` builds the image on first use. See
[firmware/README.md](../firmware/README.md).

**Release and debug builds.** `firmware/debug.h` has the flag `DEBUG`, which is 0 unless the build says
`DEBUG=1` (`tools/fw.sh DEBUG=1`, in `build/firmware-debug/`, not copied to `build/assets/`).

- A release has none of what was built to measure and to test: no timing overlay and no statistics behind it,
  no live first line, no visit, late-frame or button lines in `debug.txt`, no shortcut to the desk scenes, no
  ride (a race that cannot start goes back to the menu), and the original's gating instead of everything open
  from the start (`S2SAVE_UNLOCK_ALL`, which the Makefile sets from `UNLOCK_ALL`: 0 in a release, 1 in a debug
  build; `tools/fw.sh UNLOCK_ALL=1 TAG=open` is a release with everything open).
- What stays is the boot log, the files, the menu's and the championship's lines, the faults, the frame's
  timeline marks (microseconds; the hot code's place in the boot RAM was measured with them) and the
  simulation's own hooks.
- The simulation and the tools that read the statistics use the debug build (`tools/simcheck.sh` takes
  `build/firmware-debug` unless `SIM_FW` names another; the measuring variants `PROF=1` and `TAG=...` of
  `tools/fw.sh` are debug builds unless `DEBUG=0` is given). Wherever this file speaks of the overlay, the
  statistics of `debug.txt`, the ride or "everything open", it is the debug build.
- The debug build of the commit that brought the flag is byte for byte the firmware before it
  (`program.bin` 352,632 bytes, crc32 d745726c); the release is 345,192 bytes.
- A release is made from `tools/fw.sh` alone, so a release cannot contain the debug code by accident:
  `tools/fw.sh`, `tools/build.sh` if the hardware changed, `tools/package.sh`, `python -I tools/release_zip.py`
  (`build/release/Chainy.Screamer2_<version>.zip`, the version of `core/core.json`).

A release holds the bitstream, the core's JSON files, the platform files and the firmware,
never game data. `tools/deploy.sh <sd card> [game folder]` additionally copies your own game
files (default folder `C:/GOG Games/Screamer 2`, or `$GAME_DIR`): `SCREAMER2.zip`, `GAME.GOG`
and `GAME.DAT`, to `Assets/screamer2/common/`, and leaves everything else on the card alone.

## Game data

The game's files reach the core as ONE ZIP in one data slot (the APF allows 32 slots, and Screamer 2
has about 140 files): `SCREAMER2.zip` holds the original `DATA`, `GFX` and `ANIMS` folders, entries
stored (method 0, fast) or deflated (method 8, loads slowly; the firmware inflates them and checks the
CRC-32). The music image `GAME.GOG` and its cue sheet `GAME.DAT` stay separate slots. How a player makes
the ZIP is in `core/dist/common/README.txt` (Windows 11 Explorer, `tar`, 7-Zip). The firmware reads the
ZIP with `firmware/zip.c` (the central directory only: Windows writes sizes 0 into the local headers;
names are matched on the end of the path, ignoring case, so a folder in front does not matter).
`tools/check_zip.sh` tests the reader natively against the real ZIP and broken ones.

The core reads the container files inside the ZIP unchanged. The firmware reads three containers whole
with `zip_read` (`GFX/MAPnH01.DAT`, `DATA/MAPn.DAT`, `GFX/ENVPn01.DAT`), unpacks their entries with
`firmware/dat.c` and builds each track's image at load time (`track_build_s2()` in
`firmware/track_build.c`): the placements, the palette, the drivable parts per grid cell, the road points
and walls, the background and TRACK_DATA's far plane, and the cars of the race with their material
libraries merged after the track's (the face's material is a signed 16-bit offset from the MLB's start, so the
cars' material records are collected in a section in front of the MLB and the cars' faces point there; the
texture records and pixels stay in the cars' own `.MLB` files, appended after the track's), and the picture of
the cars' windows (below). The cars are the four of the grid, each its own team's ("Teams" below). The image is 3.5 to 5.4 MB of the 7 MB window at `0x1210_0000`. There is no camera path, no markers file (Screamer 2 counts the laps on
the line of `MAPnOPP.SPL`, which the firmware reads from `DATA/MAPn.DAT` itself, `firmware/race.c`) and none of the original's menus (the options room as the menu, "The menu" below). Nothing is converted on the PC.

`tools/s2/make_track_s2.py <game folder> <n> <out.bin>` builds the same image on the PC. It only serves
as the reference for `tools/s2/check_track_build_s2.sh [game folder]`, which compiles the firmware's
builder natively (address and undefined-behaviour sanitizers) and compares the result byte for byte, for
the seven tracks. The game folder is the unzipped original (its `GFX` and `DATA` folders): the ZIP only
holds the same files. (`tools/make_track.py` and `tools/check_track_build.sh` are Screamer 1's builder
and its reference, no longer reached by the Screamer 2 program.)

`L` and `H` in `MAPnL01.DAT` / `MAPnH01.DAT` are the game's DETAIL sets, not resolutions: the game
loads the `L` set only for LOW and the `H` set from MID on (more scenery, same textures). The core uses
the `H` sets (DETAIL HIGH), day, 256 colours (`..01`).

The core lists its files on the screen (green there, red missing and needed, grey missing and
optional) and says in plain words what is wrong with the ZIP (not found, not a ZIP, unsupported
compression: repack with Store; a deflated ZIP gets a notice that loading is slow). `GAME.GOG` and
`GAME.DAT` are optional: they only bring the music. `tools/files_screens.sh` draws these screens on the
PC (`build/check/screens/*.png`).

## Viewer (milestone 2)

After the files screen (a LOADING screen while all is in order, the list of the files with what is wrong otherwise) the core goes on by itself once the read test passed: the viewer puts the original's
LOADING picture up as soon as the toolkit can draw it and starts with the intro, the attract sequence (any button ends it), and then the menu (next section). The simulation has no menus, so `tools/fw.sh EXTRA_CFLAGS=-DS2_SIM_INTRO=1 TAG=intro` builds a variant that runs the intro there on track 1's image (`tools/s2/sim_race.sh build/sim/<dir> build/s2/track1.bin 1 600 <name>`): the LOADING picture after 31 ms, the track built in 0.7 s, the logos, then the title over the England race under the trackside cameras with the four computer cars (the last frame shows "SCREAMER 2" and "COPYRIGHT 1996"), no trap, the stack 5,360 bytes. The viewer's ride, which the simulation (`SIM_*`) runs for timing, loads a track and shows it from the game's near chase camera over a car that drives
the road at 150 km/h in a loop, with the player's car and three more ahead (`firmware/viewer.c`, `firmware/road.c`); the menu has no way to it. Frames go through the
hardware path (geometry unit, setup unit, rasterizer, blitter) with the original's level of detail at
DETAIL HIGH (`track_lod_level()`: placed meshes switch at 6,000 and 9,000 units, cars at 2,000 and 6,000;
far plane from TRACK_DATA, 50,000, track 4 60,000; pieces out to far + 8,192). The ride is silent (the race has sound and music,
"Sound" below). Start starts the driving mode ("Driving mode" below).

### The menu

The menu is the original's options room ("The options room" below, `firmware/s2room.c`, `firmware/s2menu.c`): the team's room with five stations, ARCADE, CHAMPIONSHIP, TIME ATTACK, MULTIPLAYER and GAME SETTINGS (laps, level, gearbox, ... with VIEW HIGH SCORES), and ESC for TEAM SELECTION and ENTER YOUR NAME (docs/screamer2/menus.md has the original's screens). In a debug build everything is open from the start (`S2SAVE_UNLOCK_ALL`, "Release and debug builds" above): all seven tracks, all four teams and their five cars, all four leagues of the championship; a release has the original's gating (three tracks, league 1 and four cars a team at first). If the room cannot be built (the log says so) the arcade pages stand in for it. The list that was the menu before the room (START RACE on any track at once, the ride, laps and level rows) is gone.

**The arcade pages** (`firmware/s2arcade.c`, details in docs/screamer2/menus.md section 6): title (ARCADE_L with the team's four cars driving past, "The arcade title's cars" below; ACCELERATE TO CONTINUE blinking) -> TRACK (the tracks' pictures with their banners,
the lit frame) -> CAR (a 2D stand-in for the 3D page: team, car and its name plate) -> TRANSMISSION (AUTOMATIC / MANUAL) -> the race. B or Start go on (the picture fades out over half a
second, with the page's click), A or Select go back (a cut): the TRACK page's A leaves to the options room, the CAR page's to TRACK, the TRANSMISSION page's to CAR.

| Button (arcade pages) | |
|---|---|
| B or Start | forward |
| A or Select | back |
| d-pad left / right | TRACK: the track before / after (the original's order England, Egypt, California, Finland, Switzerland, Columbia, The Tunnel); CAR: the car; TRANSMISSION: automatic / manual |
| d-pad up / down | CAR: the team (the original chooses it on an earlier page, not built) |
| L / R | TRACK: three places back / on, round |

The choices are kept: in the session, and across power-ups in the nonvolatile `CHOICE.DAT` (data slot 23), Screamer 2's save in a layout of its
own (`firmware/s2save.c`, docs/screamer2/menus.md section 7.1; `s2menu_store()` sets the track, team and car, and the laps, level and gearbox settings, also after the arcade pages
are left with A), which the
Pocket writes back when the core exits (the first start with the new firmware reads the old 1,120-byte file once and turns it into the 19,348-byte one). After the files screen the arcade pages show the last choices, so a race with the same choices is ARCADE and B on each of its four pages. The grid is applied when the track image is built (`load_track()`), so every start from the menu loads the track again
(3 to 5 s; the cars that did not change are not read again). The log gets one line per start: `menu: race T4 CONDOR 1 3L NORMAL AUTO`.
`tools/menu_screens.sh` runs the menu's code on the PC: tests of the grid, the kept choices and the texts read from the real ZIP, and of the menu's run on a stand-in room (the real room's tests are in "The options room" below); the arcade pages are compared with a model (below, Tools).

Back to the menu: EXIT in the race's pause menu (Start, "Loading screen and pause menu" below), Select + B in the ride (the music stops), and EXIT on the end screen
of a finished race ("End of the race and the two pages" below). The simulation (`SIM_*`) has no menu: it takes the track from the testbench as before.

| Button (ride) | |
|---|---|
| d-pad left / right | previous / next track (1 to 7), the track is loaded again (about 5 to 10 s) |
| A | the cars: 4 (the realistic field), 0, 1 (the player's) in turn |
| B | timing overlay on / off (default on) |
| Select + B | back to the menu |
| Start | the driving mode |

### 3D menu pages (TEAM SELECTION, ENTER YOUR NAME, the CAR page)

Menus row 5 (docs/screamer2/menus.md section 6): three pages with a few 3D objects over a 320 x 200 picture, through the geometry unit with the page's own material file (`GU_MLB`): `firmware/s2scene.c` is the toolkit (a container's entries read from the ZIP into `0x1180_0000`,
the unit set up after the picture is blitted, blocks handed on by `track_block_piece()`), `s2pages3d.c` the team and name page (one page in two states, as the original), `s2showroom.c` the CAR page's carousel, drawn by `s2arcade.c` (one page for the CAR and TRANSMISSION states). A save
without a profile (`S2S_PROFILE`) shows the team and name pages once before the menu; ESC in the options room shows them again. The pages' sounds, keys and clocks are the original's (read from `STARTL.EXE`); the log has the load times (`pages3d: LOGO1.DAT in N ms`,
`showroom: 5 cars of team 1 in N ms`).

Tests: `tools/menu_screens.sh` (scripted buttons through the pages on the PC with the geometry unit's C model, `tools/host/pages3d_screen.c`: results, sounds, the save, the first-start flow; the pictures against an independent reference with a piece builder of its own, in double precision) and
`tools/pages3d.sh` against the running original: `python -I tools/s2/dosbox_arcade.py --pages3d` takes 70 raw DOSBox screenshots of the three pages (Windows, DOSBox in front for about 2 minutes), `tools/pages3d.sh` finds for each the state of the firmware's page that draws it (the turning
objects' angles are searched) and counts the pixels that differ (`tools/host/pages3d_match.c`; pictures with `DUMP=<part of a name>` in `build/check/pages3d/`).

### The championship

Menus row 6 (docs/screamer2/menus.md section 6): CHAMPIONSHIP in the options room (the second station) runs LEAGUE SELECTION (`firmware/s2leaguepages.c`) -> WELCOME TO LEAGUE n -> the league's first race -> LEAGUE REPORT -> the next
race ... The rules are `firmware/s2league.c` (read from `STARTL.EXE`: leagues of 4, 5, 6 and 6 races on England, Egypt, California, Finland, Switzerland, Columbia in turn; the computers ROOKIE, NORMAL, PRO, NORMAL and in league 4 all on their teams' fifth cars; 10 / 6 / 3 / 0 points by place;
the league is won by being first on points after the last race, which opens the next league, one more track (league 4: the seventh when all four teams' fifth cars are won) and in league 4 the team's fifth car), the flow is the viewer's (`league_run()`). The team, car and gearbox are the start menu's,
the laps GAME SETTINGS' NUMBER OF LAPS. The race is the arcade's: a league race has the pause menu without RESTART (EXIT counts the player last), and ends on the end screen's CONTINUE (B or Start), which lists the cars that have done their laps with their times and points.

| Button (championship pages) | |
|---|---|
| d-pad left / right | LEAGUE SELECTION: the league (two of four in view); the question LEAVING LEAGUE?: YES / NO |
| B or Start | LEAGUE SELECTION: take an open league (a league that is NOT AVAILABLE does nothing); WELCOME and the REPORT: on; the end screen: CONTINUE |
| A or Select | LEAGUE SELECTION: back to the options room; WELCOME: back to the selection; the TRACK page and the REPORT between two races: ask LEAVING LEAGUE? ARE YOU SURE ? (the TRACK page before the first race goes back to the selection), YES leaves the league for LEAGUE SELECTION |

The original's TRACK page (the turning 3D map, row 7, `firmware/s2trackpage.c`) comes between WELCOME / the report and each race. The CAR page with its set-ups (row 12, below) follows the TRACK page. WELCOME flies the league's track plates over its picture and ends by itself, a won league is followed by the desk scene ("The desk scene and WELCOME's plates", below). Left out: the weather. The leagues open, the tracks opened and the fifth cars are the save's (`S2S_LEAGUE_OPEN`, `S2S_TRACKS_OPEN`, `s2save_car5_open`; no new field);
a debug build opens everything (`S2SAVE_UNLOCK_ALL` 1), so NOT AVAILABLE shows in a release or with `tools/fw.sh DEBUG=1 UNLOCK_ALL=0 TAG=x`. The player's total and best lap of a league race go into the championship's best-times lists (HI SCORES, CHAMPIONSHIP; the LOADING screen shows them). The log has
`league: 2 begins` and `league: race 3 T4 first car 0` (the car's index in the grid, 0 the player; "(player left)" when he left through the pause menu).

Tests: `tools/s2/check_league_s2.sh` (the rules on the PC with the real `s2save.c`), `tools/menu_screens.sh` (the pages and the championship's end screen against `tools/ui_league_ref.py`, scripted buttons), `python -I tools/s2/dosbox_arcade.py --league` against the running original (below, Tools).

### The desk scene and WELCOME's plates

Menus row 6 (docs/screamer2/menus.md section 6). Two 3D parts of the championship's flow, both read from `STARTL.EXE` and held against the running original frame by frame (`tools/s2/dosbox_desk.py`).

**The desk scene** (`firmware/s2desk.c`, `s2desk.h`; the page 0x3bc38). It is **not** between CHAMPIONSHIP and LEAGUE SELECTION (the options room's CHAMPIONSHIP leads straight to the selection, 0x390e4; the earlier notes had it there): it is what the LEAGUE REPORT's ENTER after a *won* league leads to (0x44144), and from it the selection comes back; after league 4 a second visit follows if the team's chosen car is not the fifth (0x3bf06), which shows scene 4 with the fifth car and makes it the chosen one (`s2desk_won()`, called from `league_run()` in `viewer.c`). The league in hand picks the file `ANIMS/SCENE<nn>1.DAT` (the 1 is the resolution): leagues 1, 2, 3, 4 show nn 1, 2, 3, 3 and the second visit nn 4. A file holds four maps `MAP1 .. MAP4` (the player's team picks `MAP<team>`: one room, four colour schemes), `SPLINES.PTH` and `SPLINES.TXT`, `ENV.MLB` (the car's windows); the car is `AUTO<chosen car>` of `ANIMS/SCCAR<team>1.DAT` (not the CAR page's mesh: 18 to 29 KB against 36 to 51 KB, one level of detail).
- the paths are told by the kind at header +0x60 (& 7): 1 `Camera0n`, 2 `Camera0n.target`, 4 the object `MV_mauto`; the cameras form a chain by n (scene 4 cuts between three, each over the share of the run its header +0x28 .. +0x2c spans: 0 .. 0.133, 0.133 .. 0.333, 0.333 .. 1); the camera is the path's place cut to whole numbers and the look from it at the target's (`s2scene_look_at()`, the options room's), the lens the room's (centre 159, 100). The car of scenes 1 to 3 (kind & 8) stands at the first keys of its channels with the heading of header +0x50 (338.5, 27.2 and 0 degrees, +0x48 and +0x4c, pitch and roll, are 0 in all four files), the car of scene 4 drives along its path (y from 6,903 to -588) with its header's heading (0) and wheels that turn 0.7 times a second;
- the scene lasts SPLINES.TXT's first number (6, 8, 8, 12 s: t goes up by dt / seconds a frame, 0.02 s a frame as the page sets it, the page never measures its frame time), the textures' clock its second (6.5, 3, 3, 12.2 s a turn); from t = 0.98 on, or on ENTER (a fresh press; ESC and the arrows do nothing), the picture fades out over 25 frames, the scene running on; the sound is MENU.DTR 14 (not in scene 4); no text, no sprite: the picture is the engine's alone (`track_draw_cam` with the car as an object, which sorts it in among the room's pieces by its 300-nearer key as for a race car, and by its mesh's class key: every car of the four `SCCAR<team>1.DAT` has 500 in its header's entry 43 (-500; the race's and the menus' cars of `CARS<t>01.DAT` and `CARS<t>11.DAT` have 0), 800 together, which is the class of the figures that stand round the car in all four scenes (entry 43 = -800), so the car and they are sorted by their places. Until 2026-11-14 the page gave the car no class key and the figures were always drawn after it: the legs of the ones behind the car showed through it, seen by the owner on the Pocket in scene 2 and not in a video of the original);
- the room is built as the options room is (`track_build_s2()` without cars into the track window) from a container of its own that the firmware writes: the five entries `MAP<team>.MMP .UNR .COL .MLB .BCK` read **as stored** by range from the ZIP into one buffer with the directory that `dat.c` reads (`desk_map()`), so the builder unpacks them from there and the whole file is never read. The car's `.MLB` is drawn with its own material file (the piece hook `desk_piece()` switches the unit's `GU_MLB` for the car's pieces and back; the rasterizer is drained at each switch, twice a frame), its windows with the scene's `ENV.MLB` as the CAR page's (`s2_env_write`). The block of 515 vertices of each scene is cut by `gu_split()` like any block over the limits; nothing here knows of the limit.

**Cost** (counted from the files, not timed on the Pocket). *Loading*, once a scene, with the screen black: `desk: S1 T1 c2 1041236 B read, image 2258432: read N, build N, car N ms` in the log. Read from the ZIP: **1.04 to 1.19 MB for scenes 1 to 3** (the five entries 0.99 to 1.17 MB + 11,200 to 11,800 bytes of paths, `ENV.MLB` and the file's last 4 KB) and **0.20 to 0.25 MB for scene 4**, plus the car's 36 to 50 KB, **against the files' 4.21, 4.76, 4.26 and 0.90 MB**: 3.1 to 3.6 MB less, 2.6 to 3.0 s at the Pocket's 1.2 MB/s. The builder unpacks 2.02 to 2.44 MB (scenes 1 to 3; 0.61 to 0.67 MB scene 4): about 0.5 to 0.6 s at 4 MB/s (`dat.c`: 18 cycles a byte), the image is 2.26 MB (scene 1, team 1) and its CRC-32s about 0.3 s: **about 2 s for scenes 1 to 3 (0.5 s for scene 4)** against about 5 s for the whole files, with a black screen as the room's. Memory: the 4 MB container region at `0x1280_0000` holds the container (1.1 to 1.3 MB), the track window the image (2.3 to 2.6 MB of 7), the 2.75 MB of the 3D pages' models the car (the `.MLB` of 103 to 139 KB unpacked, the `.3DX` of 18 to 29 KB, 65,792 bytes for the windows); the paths' set (9 KB, as the ARCADE title's) and the buffers of the paths file (4 KB) are bss. *Per frame* (counted on the PC with the geometry unit's C model, every 5th frame of each scene, `ALL=1` of `tools/desk.sh`: all 16 scenes of the 4 teams): scene 1 hands the unit **105 pieces and 1,050 to 1,090 faces on average (120 and 1,160 at most)**, scene 2 118 pieces and 1,430 to 1,460 faces (145 and 1,630), scene 3 98 pieces and 1,070 to 1,120 faces (126 and 1,260), scene 4 22 to 28 pieces and 280 to 410 faces (31 and 530): against a race frame's 218 pieces and 1,146 faces (12.2 ms in the simulation, with the physics, the sound and the rest); the desk scene has the paths (a handful of cubic evaluations, a square root and two arc cosines for the camera's look) and the car's 12 to 16 blocks to make, nothing else, so a frame is well inside the 20 ms (not timed on the Pocket: `tools/s2/sim_race.sh` is the main session's).

Tests: `tools/desk.sh` (`tools/host/desk_match.c`, `tools/desk_shots.py`): the recording of `python -I tools/s2/dosbox_desk.py report` (the way a desk scene is reached in the running original: one league race of one lap with the player's car handed to the game's driver, the end screen, the LEAGUE REPORT, whose state word 0x1324c4 is set to "won" so that its ENTER takes the finish branch to the desk scene as a won league's does; DOSBox in front for about 5 minutes) of scene 1 (team 1, the team's second car) and of scene 4 (the league in hand and the team's chosen car set as the first visit's end sets them): every recorded row against the firmware's scene run from frame 0, **scene 1: 2,731 rows, 2,495 are one frame of the scene exactly, 236 are rows the poll read while the page was writing them (each number is that of the frame or the next), none differs; scene 4: 4,581 rows, 4,210 and 371, none differs** (the rows hold the camera record, the textures' clock, the car's place and angles and the wheels' phase), the fade's flag clear up to frame 293 and set from 297 on in scene 1 (the poll misses frames while a screenshot is taken) and from frame 588 in scene 4, **the firmware's 294 and 588**; a negative control (every 50th row moved by one unit: 53 and 86 rows found wrong); the screenshots drawn as the firmware draws the state of each (scene 1: 3 shots, scene 4: 7): 94 to 96 % of the edges of the screenshots' colour ramps (on average, 87 to 98 % a shot) have one of ours within a pixel and the other way round; **61 % of the pixels differ in scene 1, 44 % in scene 4** (the original fills textures affine, the unit is perspective-correct, as in the options room; the colour ramps' histograms of a frame of scene 1 agree to a few tenths of a shade); `ALL=1`: the container the firmware writes builds **the very image the whole file does, byte for byte, for all 16 scenes of the 4 teams** (0.82 to 2.81 MB), and the five cars of each team load; `tools/menu_screens.sh` (`tools/host/desk_screen.c`): the four scenes run by the page runner from the real files (frames: 1 + 294, 392, 392, 588 + 25 of fade), ENTER and Start end it through the fade, ESC and the arrows do nothing, the sound, a scene the ZIP lacks shows nothing, `s2desk_won` for each league (this found the first version's scene 5 for league 4's second visit)

**WELCOME's flying plates** (`firmware/s2plates.c`, `s2plates.h`; the page 0x39569, set-up 0x35b9e, frame 0x35cc8, end 0x36168). The plates are `GFX/PLATES1.DAT`'s `A<n>PLATE.3DX` (seven flat cards, one block of 5 KB each, the tracks' posters of 184 x 232 texels, `PLATES.MLB` 426 KB; not `MAPS1.DAT`'s maps: the first reading was wrong): one for each race of the league (race i is the track `s2l_track(i)`, plate `A<track>PLATE`), 4, 5, 6 or 6 of them. Every frame, in the original's order: the league's picture, each plate's object put into the list and moved (0x35cc8), the keys, the end test, the camera at (0, 100, 1300) with all angles 0, the engine's list drawn alone, then the dark band and the two lines over it. A plate's time u is 1 + 0.6 i and goes down by 0.011 a frame: *in* (u down to 0.05): x = (1 - cos(u pi / 2)) X - 2200 u cos(2 pi u), y = (1 - cos(u pi / 2)) Y - 2200 u sin(2 pi u), z = (1 - cos(u pi / 2)) 2000 with the aim (X, Y) = (-2000, -2500) for even i and (2000, 2500) for odd, roll a2 = 512 u (the plate comes from behind the camera on its edge and turns flat to the viewer as it settles at the middle, whole numbers cut); then *out* (u = 1 - u): from where it is to (7000, -1000, -2000) for even i, (-6500, -1000, -2000) for odd, x = x0 - (x0 - X') (1 - sin(u pi / 2)) + 1500 u (1 - cos(2 pi u)) and likewise y and z, the pitch and roll growing every frame by 102.4 and 307.2 (1 - sin(u pi / 2)) of 2048ths; done at u < 0.05 again. ### Wheel smoke and shadows

All four cars throw wheel smoke off the line and on loose ground and have a shadow, as the original does at DETAIL HIGH (the core draws as at HIGH; DETAIL LEVEL keeps its value and nothing else).
`firmware/s2fx.c`, the rules read from `STARTL.EXE` (`0x204ae` the spawn, `0x2073b` each frame, `0x1f4a7` the shadow, `tools/dis.sh -f`) and held against the running game's memory:
- **Smoke.** The car's timer adds 0.02 a step while it is under 0.05 (a spawn every 4th step while the car is on the ground); then, for each rear corner of the body, if the tyres slide (slip `+0xc34` under 0.93) or the road kind's flag 4 is set and the speed is over 20, a puff of `asmoke` (kind flags & 3 = 1) or `a2smoke` (2) takes the first free of eight records of its kind: the corner's place with the ground's height, moved sideways by `((2 d & T) - d) x (x & 7)` and back by the same x `(z & 7)` (d the road kind's dispersion, T the 100 Hz counter, x and z the car's whole-number place). The spawn sees the car as the step before left it, the slip the step has just worked out. A puff lives 30 frames (its age grows 2162 of 65536 a frame, the game's step 0.022 x 1.5), stays where it was born, faces the screen and shows frame `6 x age` of its texture (80 x 60, six frames: `MISC.MLB`). The camera's car's puffs ("carried") are kept in the car's own frame (the spot turned by minus the heading, then by the pitch, cut to whole numbers) and move with it. `ASMOKE.3DX` / `A2SMOKE.3DX`: one square 588 x 568.
- **Shadow.** `ASHADOW.3DX` (one flat quad 792 x 1,534), 30 units further from the camera than the car along the ground (cut to whole numbers), 2 under the ground under it, with the car's heading and tilt, sorted 200 further back.
- Everything is seen through the see-through table (routine 224 of the hardware: the texel picks the row, the pixel goes through it) and nothing reaches back into the race (the effects only read the cars' records: `s2car_fx()`).

**The table in 64 rows (the design question).** The original makes a 112-row table of 256 at the race start (the palette moved towards `asmoke` in 32 rows, towards black in 16 (the shadow), towards `a2smoke` in 32, brighter in 16 and towards white in 16: `0x506c2`, `0x50a8e`) and its filler reads `SMG[texel x 256 + pixel]`; the hardware has 64 rows and six bits of texel (and blends routine 224 only: the game's 208 is a plain textured face to the unit). No hardware change was made. Instead `firmware/smg.c`, once where the image is built (`track_build_s2()`, the one place every library's materials pass), scans the see-through materials of the track's MLB, the cars' libraries and `MISC.MLB` (one more library, its records in front of the MLB like a car's), gives **each distinct texel the textures use a row of its own** (rows 1 to 62; row 63 stays the radar's of the Screamer 1 code), copies the texture with its texels as those rows (a texture can be shared with a material that draws its bytes as colours: the lamps of track 7 and of the night looks are, so the pixels are copied, not changed) under a record of its own with the material turned into routine 224, and puts the table, the three meshes and a directory at the end of the MLB section (`"S2FX"`, `track_fx()`; `smg_load()` writes the table into the rasterizer when a race or a room starts). A texel of 112 or more (the original reads past its table there) or of a ramp the race does not make is texel 0. With more than 62 texels the closest pair of one ramp merges (the lower into the higher).
- **Nothing is lost on the day tracks.** The art uses 25 levels of the smoke's 32, 10 to 15 of the shadow's 16 and 0 to 14 of `a2smoke`'s 32: 40 to 52 rows on tracks 1 to 6 (track 7: 80 texels with the lamps' glow, 62 rows after one merge). The table equals the game's rows for those texels: the game's own table, dumped from its memory at 6 s and at the end of a race, equals `smg_ref.py`'s reading in 28,380 of 28,416 entries on track 1 and in 28,369 on track 3, **every one of the 36 and 47 others an exact tie** (two palette colours at the same exact distance: the game's float arithmetic breaks the tie by rounding noise; ours picks the first). Had the first plan (16 equal steps for each effect) been taken, 10 to 22 % of the smoke's palette indices (4 to 8 % of the shadow's) would differ, with a mean colour error of 0.3 to 0.55 of 63: `python -I tools/s2/smg_budget.py <game folder>`.
- **The row budget** (62 rows; `smg_budget.py`): tracks 1 to 6 by day need 49 / 50 / 40 / 49 / 49 / 52 (the rotor and the second smoke's texels included: the rotor of tracks 2, 3 and 6 is `MISC.MLB`'s material of 20 frames with 13 to 15 levels of the shadow's ramp, which share rows with the shadow), so **10 to 22 rows are free**; track 7 needs 62. The **night looks** (not built) need more: 62 rows after 3 merges (track 1), 18 (track 2), 8, 3 and 20 (track 6), because the headlights' cones (14 levels of the brighter ramp, in `MISC.MLB`) and the lamps' glow (16 of the white ramp) come on top: each merged pair is a step of 1/31 or 1/15 in a ramp. The options rooms need 15 (the shadow's ramp: the shadows on their floor now blend instead of drawing as opaque colours).
- **How a later effect hooks in:** its materials only have to be in a library the image builder passes through the step (the track's MLB or `MISC.MLB`, routine 208 or 224, texels as the game's rows 1 to 111): they are copied, converted and given rows with no code of their own (the rotor and the lamps' glow of the track's own MLB already are; nothing draws them yet). Objects of the image reach the draw as `struct track_object`s as the shadow and the puffs do (`s2fx_objects()`); a mesh the effect needs goes into the effects block in `track_build_s2()` and in the reference `tools/s2/make_track_s2.py` (three meshes now).

**Compared with the running original** (Windows, `python -I tools/s2/dosbox_smoke_s2.py <track>`: the game's own arcade race on a private copy at DETAIL HIGH, the player's car handed to its driver, every frame's four cars' records, the objects and the camera read from DOSBox's memory with `tools/dosram.py`; `tools/s2/check_fx_s2.sh` replays it through `s2fx.c`). **Cost** (counted, not timed on the Pocket; `check_fx_s2.sh` counts the pixels and faces of the effects' pieces through the model of the geometry unit on the recordings; the whole merged build in the simulation is below): track 1 draws 10.3 pieces and 8.6 faces a frame on average (36 faces at most) with 10,700 blended pixels (48,400 at most), track 3 27.5 pieces, 20 faces and 21,100 pixels (44,600 at most). piece, while the rasterizer finishes the picture. `-DRACE_OVERLAP=1` runs them all after the last piece, `-DRACE_OVERLAP=0` before
the scene as one step with the player's. Where the hardware is the bound, which the worst frames are, the CPU waits for it anyway and
the steps cost nothing; the computers' cars are drawn from the step before (`road_race_scene` copies their poses before the first slice). See
docs/screamer2/driving.md, "The race", and performance.md section 7 for the numbers.

The physics sits behind `firmware/s2car.h` (`s2car_init`, `s2car_step` for one 20 ms step, `s2car_look`,
`s2car_camera`; the header is the contract with the car physics). `s2car.c` is the game's car model (docs/screamer2/driving.md). Until `firmware/s2car.c`
exists the Makefile builds the kinematic stand-in `firmware/s2car_stub.c`: speed from gas, brake and drag (top
speed 200 km/h), a yaw rate from the wheel angle, the car on the surface under it (`track_under`) and tilted by it,
five gears of 40 km/h, a camera behind and above as the ride's. It is not a model of the game's car (no
grip, weight, reverse, walls or fall: with no ground under it the car keeps its height). With `s2car.c` present
the Makefile takes it and every other `firmware/s2car*.c` instead (`S2CAR_SRCS`, also settable on the command
line); `tools/s2/render_s2.sh` and `framestats.sh` do the same. `yaw` grows to the left (the view turns left),
so steering left (-1) must increase it. The race (`firmware/race.h`) uses more of
the physics' side of the header (`s2car_init_grid`, `s2car_init_at`, `s2car_step_driven`, the `hold` and `ai` fields of the state):
the stand-in does not have those, so a build without `s2car.c` does not link.

The overlay (top left, drawn after the 3D picture) shows the mean and the worst time of a frame over
the last second in ms, the track, the cars and the faces of the frame. A frame's time runs from its
start (the swap before it is done) to the end of the rasterizer's work (in the driving mode including the CPU's part of the race screen, docs/screamer2/hud.md,
which is made while the rasterizer works, but not the overlay's own text), not including the wait for the next
vertical blanking, so 10 ms still shows 50 pictures a second; the camera advances by the real time
(video frames of 1/50 s), so a frame over 20 ms makes the picture slower but not the movement.

### Sound (the race)

The race has the game's music and effects (`firmware/s2sound.c`, rules in `firmware/s2snd.c`); the ride is silent. The
rules are read from the original's program (`STARTL.EXE`, addresses below; OpenScreamer's `docs/NOTES2.md` S2-5zf has
the sound manager) and tested natively (`tools/s2/check_sound.sh`).

| What | When | The rule (STARTL.EXE) |
|---|---|---|
| Music | with the race: the track is set up (before the lights), round and round, goes on through the end screen (the original's CD is never faded, menus.md "The sounds of the end screen"); stops when the race is left | the CD track is `CD_TRACKS` of `DATA/GAME.DAT`'s `MISC.DTR`, `9 8 6 7 4 3 5` for tracks 1 to 7 (`0x2ebc9..0x2ebdc`: `CD_TRACKS[track - 1]`, the repeat flag set); the CD image `GAME.GOG` and its cue sheet `GAME.DAT` are the optional pair (data slots 22 and 21), `firmware/music.c` streams it through the mixer's ring |
| Engines | all four cars, from the first frame (the grid's revs too); in combat mode each of the two from its own player's camera (`0x1fe18`) | per car a voice: sample = the car's model (`M_PORSCH`, `M_CELICA`, `M_ACUV1`, `M_MK5` for the four cars; `M_STOCK` .. for a team's fifth model), the same recording's tunnel version (`T_*`, sample + 0x19) on road kinds 7, 13, 34, 43 (`0x1fe3b..0x1ff20`); rate = the sample's own x (2 x revs / most revs)^2, plus that x (last distance - distance) / 50,000 x 5; volume = the sample's x ((50,000 - distance) / 50,000)^2; pan = 32768 - 32767 x cos((1 - across / 50,000) x 1.87): the listener is the picture's camera (`0x1ff20..0x1ffb3` fills the call's record, the routine is `0xaf338`; the constants were read in the program: 2.0, 5.0, 1.87, 32767, 32768) |

`DATA/SOUND.DAT` (1.4 MB) is a `.DAT` container of `.RAW` samples (8-bit unsigned mono, stored) and `.DTR` tables;
`GAME.DTR` lists the 33 samples of the race by number with their own rate (8,000 to 22,050 Hz), volume and loop, in a section
`SOUND_DATA` (`sNAME.RAW xID xLOOPLEN xLOOPCOUNT xVOLUME`, then `dRATE dBITS dCHANNELS dFORMAT`). It is read whole from the ZIP once,
when the viewer starts (about a second on a stored ZIP, longer on a deflated one), to `0x11C0_0000` (docs/soc.md), and the
mixer plays the samples straight from there. The mixer's step is the rate over 48,000 (2.16), at most 4 samples a value. `MENU.DTR` and the
`AMBIENT*.DTR` of the tracks (birds, mill, crowd, ...) hold the scenery's samples ("Animated scenery" below); `MENU.DTR` is the menu's.

Voices of the mixer: 0 to 3 the engines, 5 the player's tyres, 6 to 9 the knocks (round robin). Volumes: the sample's volume (`0x3fff`
for the engines, `0x5fff` for `M_ACUV1`, `0x7fff` for the rest) times the game's factor, then the effects' master `S2SND_FX_MASTER` `0x2000`
of `0x7fff` (Screamer 1's `sound.c` has two thirds of the game's, `0x4000`; with that the four engines and the tyres alone clipped
the sum in the first simulation, 686 samples in 8 s, so it is halved; a full sample at the full volume then moves the output by 63
per 8-bit step, the music stays at `0x4000`), pan with the far side faded linearly. The game starts a new voice for every frame of a contact and lets the old
ones play on; here a knock starts every 3 frames at most (a harder one at once). The engine of a car at rest has a floor of 200 Hz.

The cost: `s2snd_frame()` (the engines, tyres, knocks, the scenery) and `music_frame()` (the ring) are timed with the cycle counter
and the mean and worst go into the log (`sound: 250 fr, effects 7211/7519, music 643/950 cycles mean/max`) five seconds into the
race and when it is left. In the simulation of the race on track 4 (330 frames, 4 cars, the music's ring filling): the effects
7,211 cycles on the mean and 7,519 at the worst, 0.10 ms; the ring 643 and 950 cycles, 0.01 ms. They sit before the scene in the frame, so the first mark of the
timeline (`ph` in the log) holds them; that run: 13.6 ms mean and 15.1 ms worst a frame, no frame over 20 ms, 50.0 a second, with the
computers' steps after the scene (`RACE_OVERLAP` 1). The ring was read as the song played: 51 reads of 32 KB or less for 330 frames,
by the log's `data slot read 22` lines, at the rate of the song. Track 1, 260 frames: effects 7,027 / 7,356 cycles, ring 638 / 956,
12.6 ms mean and 13.6 ms worst a frame, none late. Stack of the program 4.5 KB. (The runs: the real ZIP, a made-up CD image of
tones and the commands of "Simulation" above with `SIM_WAV=build/sim/race1.wav`; 330 and 260 frames take 13 and 10 minutes.)

What the output showed (2026-11-04, `SIM_WAV`): the music is the track's song: track 4 reads CD track 7 (its first read at the
sector of track 7) and track 1 CD track 9, whose two test tones (1,800 and 2,700 Hz, amplitude 12,000) came out at 5,950 of the 6,000 the
music volume gives. The engines were there from the first frame of the race and louder with the cars let go. At the effects' master `0x4000` (first run, the
music silent in it, a track without a tone) 686 samples clipped in 8 s; at `0x2000` (second run, with the tones) the peaks were 21,800
and 27,200, nothing clipped, the engines' rms 3.5k left and 5.2k right (the game's pan leans right: a source straight ahead is
at 42,400 of 65,535) against the test tone's 4.2k.

The music and the track load: the load takes the data slot for 3 to 5 s (the ZIP's reads), the ring is read from a data slot too,
and the ring holds 1.2 s: so the music stops when the race is left (`s2snd_stop()` in `leave()`, which waits for a running read of
the ring) and starts again with the next race (no 170 ms first fill any more: "The menus' music" below). A
restart of the race on the same track (the pause's RESTART, RACE AGAIN and REPLAY after the finish: the song is no longer faded out at the finish) keeps its song. A frame as slow as 1 s would still not run the ring dry.

What is open: the original's volume balance is not known (the CD drive's analogue mix is not in the program; the two thirds are
Screamer 1's choice), the pan law of the effects is HMI's as Screamer 1's `sound.c` has it, the car against car knock is the
firmware's closing speed, an obstacle's knock is sample 0x10 (the middle crash) when the player's car hits one ("Obstacles and sparks") and the scenery's sounds have no Doppler (the game asks for their rate with a pitch of 0, "Animated scenery" below), no menu sounds in the start menu (the clicks of `MENU.DTR` exist, `s2sound_menu()`, the pause menu uses them), the pause eases the effects out in 0.75 s (above) and the end screens in 1.5 s once their choices are up (`s2end.c`, menus.md).

### The menus' music

The original plays CD track 2 between the races (rules read from `STARTL.EXE`: menus.md, "The menu's music": it begins with the end of the attract sequence and the end of every race, the desk scene and GAME SETTINGS' MUSIC row restart or stop it, a race and the attract sequence stop it, no page touches it, nothing fades it).
The core plays it from the same ring as the race's songs (`firmware/music.c`), which makes two problems that the original's CD does not have: the ring is the CPU's work, and its reads share the **data slot** with every blocking read of the program (the ZIP's: a page's picture, the options room's 1.5 s build, the cars, the desk scene).
What is built, with the reasons:

- **One place for the blocking reads.** `slot_read`, `slot_size` and `slot_set_size` (`slot.c`) call `slot_hook(len)` before they use the slot; `music_init()` sets it to `slot_guard()` (`music.c`). The slot does one read at a time (`slot.h`), so a read of the ring that is running is waited for and taken (a few ms) and the two never meet.
  No page and no feature knows: every ZIP read of every page, the loading screens and the track build go through it (`zip.c` reads only through `slot_read`).
- **A song that a load would starve is held, not stopped or faded** (the choice, with reasons): the guard computes the ring's live lead (what is written less what the mixer has played; 1.2 to 1.45 s right after `music_frame()`, 0.55 s right after a start) and holds the song when the call would leave less than
  `need` = the read's estimated time (100 cycles a byte, 0.74 MB/s, slower than anything measured: 2.4 MB in 2.1 s, 32 KB in 25 ms) times 1.7 (the CPU's work on the bytes afterwards: the Pocket's logs have the room's and the tracks' builds as long as their reads, the estimate is slower than the APF, which pays for it)
  + 0.3 s; and when 0.5 s have gone since the last `music_frame()` (a chain of reads that each pass, a ZIP entry's 64 KB chunks with the inflating between them: the work after the last chunk, the room's build, must find 0.7 s in the ring or the song held). Held is `music_pause()`: the mixer stops and the place is kept to the sector (`origin`, the song's byte that the ring's frame 0 holds, keeps it right over any number of holds), and the next `music_frame()` resumes it with the first fill again. The alternative, stopping the song for good until the page asks for it, would need every page to know about every load; fading would make a gap that is not in the original either.
  A song that is only starting (priming) is never held: nothing plays, a long read only delays it. A held song is a gap of the load's length (the options room's 1.5 s when it is not in memory, the desk scene's 1.0 to 1.2 MB read, the cars' 0.5 s if the ring is low) and about a tenth of a second; where the CD plays through. The log has `music: held for N ms by a load` (the first eight).
- **Short reads do not chop the song.** A page's picture or sprite sheet (up to 64 KB, 90 ms by the estimate) always passes; a read of up to about 380 KB passes on a settled ring (the lead is 1.19 s at the least, the read must leave its 1.7 times its estimate and 0.3 s). The page tests count them: of 1,919 reads of 64 KB or less in the tests' flows none held the song within a quarter of a second of the last `music_frame()`
  (the 16 reads of up to 4 KB that held it were in chains of loads that had gone 0.5 s without one).
- **The ring is kept filled in every page loop.** `s2page_run_step()` (the page runner: all 2D pages, the 3D pages, the options room, the CAR and CUSTOMIZE pages, the desk scene, WELCOME's plates, the track pages, GAME SETTINGS, the pause menu) calls `music_frame()` once a frame, first thing after the frame wait;
  `s2load_fade()` (the loading screen's fade) calls it; the race (`s2snd_frame()`) and the attract sequence did already; the pause menu's own call is gone (the runner has it). The cost is the race's, which measured the ring at 643 cycles a frame on the mean (0.009 ms) when a song plays; a few cycles when none does.
  `tools/menu_screens.sh` counts the calls against the frames of the runner (`check_runner`, `check_pause`: one every frame, fades and cuts too).
- **The start is in pieces.** `cd_start()` no longer fills 224 KB waiting (the 170 ms that showed as a 200 ms step when a race was started again): it starts the first read; `music_frame()` takes a read in and starts the next, one a frame, and starts the mixer when 96 KB (3 reads, 0.55 s of music) are in.
  The mixer is off until then, so nothing of the ring's old content is ever played (the risk the first reading of this saw), and no frame waits; the song is audible 9 frames (0.18 s) after it is begun at the model's 1 MB/s. This is for every song: the menu's, the race's (`s2snd_music()`), the attract sequence's cue, a held song's resume.
- **Where the menu's song begins** (`s2menumusic.c`): `s2mm_page()` from the page runner when a page begins outside a race (`s2snd_racing()`: the pause menu and the end screen are pages of a race) and no song plays or waits, MUSIC ON: a page follows every start of the original's table, and the song then begins where the page is up instead of in front of a load. `load_track()` stops it
  (the race begins); the race's end stops the race's song (`s2snd_stop`), the pages that follow begin the menu's. `s2mm_song()` restarts it: the desk scene after its scene is loaded (`s2desk.c`, `0x3bd29`) and GAME SETTINGS' MUSIC row when the value changed (`s2pages.c`, `0x42462` / `0x42451`: ON from the beginning, OFF silence).
  A page change does not touch it. FM songs (`MUSIC.DAT`, not in Screamer 2) are not held: they use no data slot.

**What a long CPU stretch without a slot call does:** nothing can hold the song then; the ring lasts 1.2 s at the least (the model's negative control shows the repeat at 2.5 s and none at 1 s). The guard assumes that after a read it let pass the CPU is back at a `music_frame()` or another slot call within 0.3 s (six frames) plus the work on the bytes it counted,
and that no CPU-only block of a second or more follows a short read. Known CPU-only blocks: the builds of the room, the desk scene and the tracks come after container reads of 0.8 MB and more (held); the darkening table (70 ms) and a page's first frame are far below. The Pocket's log says if this is wrong: `music: CD track N ran short of data in M frames` (existing since the first race).

setting keeps only its value). In the race (the arcade's, the championship's, time attack's, the replay), not in the viewer's ride.

**The rules** (read in the program, written again in Python, `tools/s2/anim_ref.py`, and compared with the running original, below). A path is `MAPn.PTH`: a count, then per path 100 bytes (the name `MV_<c>..`:
`c` is the path's number, `1` to `9` are 0 to 8 and `a` on 9 on, not its place in the file; the floats at `+0x28` and `+0x2c` are the span of the run that its keys cover, 0 to 1, but 0 to 0.5 for the trains and
Columbia's birds, which are at the end of their path from half the run on: `0x129d5` reads the channels at `part / span`) and three channels, x, y and height, each a list of keys (time 0 to 1, value, the slopes out and in); between two keys
the value is the cubic with the controls `v_p`, `v_p + out_p h`, `v_q - in_q h`, `v_q`, h a third of the time between them (`0x126ad`); the way is the three channels' rates made a unit vector (`0x129d5`). A row's run
is `(race clock - start) / seconds`, and the row is **alive** when the player (his car's whole-number place) is within 52,000 units of it in x and in y or, a row that has an object and neither of the flags 1 and
2, always; and it must belong to the lap (`row.lap`: the player's lap counter + 1, 0 any). Flag 1: it starts when the player comes within its range (-1: 52,000), so it is not there before; flag 2: it runs once
(the birds: a flock a lap); a flag-1 row that has run waits to be set off again; flag 0: it runs round and round, whether the player is near or not. The race clock is the steps run x 20 ms (the original's
`0x13335c`: 0 at the grid, the lights are out at 3 s, so the helicopter of Egypt comes 7 s into the racing). A row's place is truncated to whole numbers (`0x2cee4` stores it so, in the row and in the object's record);
its heading is the angle of the path's way on the ground, `atan2(x, -y)`, and its climb the angle of the height against what is left of the way along the ground once it is turned back by the heading, both in
2048ths of a turn (the object's `+0x18` and `+0x14`, roll 0; `anim_ref.py` has the program's own steps). A row with the flag 4 (the birds) is not turned along its way: it faces the screen (the engine's
billboard: the camera's heading less a half turn, its pitch, its roll the other way). An `@` row has no object: its sound stands at the first place of its path.

**Drawn** as the cars are, as objects of the scene (`s2anim_objects()` after the cars in `viewer.c`; their blocks are made when the drawing comes to them, `car_mesh_draw()`: the blocks' places in the mesh, the
original's order for a moving object's blocks, its level of detail at 2,000 and 6,000 units; the key of the sort 300 nearer than a piece's, as a car's). The meshes are `GFX/MAPnH01.DAT`'s `A1BIRDS`, `A2BIRDS`, `AELI`,
`ADIRIGIB`, `ACABLE`, `ADOZ`, `A1TRN`, `A2TRN` (`.3DX`, 0.9 to 11 KB, 20 KB at most a track, unpacked at the load into the program's memory). **Their materials are the track's `MISC.MLB`, not its `MLB`**
(the helicopter of Egypt: records 272 to 352 of `MISC.MLB`), and the geometry unit takes a face's material at a signed 16-bit offset from the `MLB`: so the track image holds `MISC.MLB` as one more library after
the cars' (its records in front of the `MLB` after the cars', its textures after the cars' libraries; `track_build_s2()` and `make_track_s2.py`; the image grows by 74 to 136 KB), and `s2anim_load()` moves each
mesh's faces onto those records by the builder's `misc_delta` (`s2_faces_onto()`, the cars' routine). The helicopter's rotor is a second block (`fai`, a flat quad of 5,600 units) with a **routine 208 material of 20
frames** (64 x 64, the disc as texel values 33 to 41, 0 outside): a see-through material that turns with the texture clock (the geometry unit's frame is the frames x the clock; in a race `viewer.c` runs the clock as the original's `0x4b149` does, by 0.3 of the step's length a frame,
a turn in 3.03 s at the original's step of 0.022 s; until 2026-11-13 nothing ran it in a race and the rotor stood still, as did every texture with several pictures and every mesh with frames;
the object has no frames of its own, header `+0x10` = -1); the body has two more faces of it (the tail rotor). **That part needs the see-through table** (the game's routines 224 / 208): the geometry unit draws routine 208 as an opaque picture (a black square with a sand-coloured disc in it,
palette entry 33), so the image builder's see-through step (`firmware/smg.h`, "Wheel smoke and shadows") turns the rotor's material, as every material of routine 208, into routine 224 on a copy of its texture with
the texels as the table's rows (14 texels on tracks 2, 3 and 6, `check_anim_s2.sh` checks the copy), and the rotor and the tail rotor are drawn through the table like the smoke: a translucent disc over the body, as in the original's screenshots.

**Sound.** A row with a sample (the fourth column: a sample of the track's `AMBIENT<n - 1>.DTR` in `SOUND.DAT`, numbered from 0x40: bird, mill, horse, crowd, market, waterfall, jungle, helicopter, works, traffic,
tram, train, wolf, cow; the `SOUND_FX` list of the `.DTR` is empty on every track) has a looping voice while it is heard: an `@` row while it is alive, an object while it is shown. It is heard from the camera within
80,000 units, the volume the sample's x ((80,000 - d) / 80,000)^2, panned by its side, the rate the sample's own with the Doppler shift of an engine's (the engines' rule, `s2snd_heard()`); voices 11 to 31 of the mixer, one for each row (at most 9 rows are heard at once on the
longest tour of any track; the samples are in `SOUND.DAT`, read once with the effects). Measured in the running original (`dosbox_anim.py <track> --voices <seconds>` samples the sound manager's slots and the
driver's voice records every 100 ms): the rows' voices are slots 7 up in the order of the rows (the crowd of Egypt's fourth row is slot 10), a voice farther than 80,000 units has its rate 11,025 and no volume, and a voice

`AMBIENT` table (35 samples) by two readings. The pictures: `python -I tools/s2/anim_shots.py <track>` draws the firmware's scenery for the state of each screenshot of a recording (`render_s2.sh`'s camera letter `a`)
and compares what the objects cover.

### Obstacles and sparks

The cones along England's bend, California's striped fences and cones, Egypt's chests and crates, and the sparks of two cars touching or a car's knock against a wall, as the original has them at DETAIL HIGH (the core always draws as HIGH; DETAIL LEVEL keeps its value and nothing else). `firmware/s2props.c`; the rules read from `STARTL.EXE` (`0x30a4e` / `0x30b29` the set-up, `0x2a639` the car against them, `0x2c475` their flight, `0x2aeb9` the sparks' throw, `0x2cc70` their flight, `0x2b9b1` the frame that calls them; `tools/dis.sh -f`) and held against the running game's memory.

| Track | Obstacles (`MAPnDAT.DTR` OSTACLES rows, `MAPnOST.SPL` places) |
|---|---|
| 1 England | 23 cones (`AZCONE`), a line down the middle of the road at a bend |
| 3 Egypt | 48: 36 chests (`AZCHEST`), 12 crates (`AZCRATE`) |
| 4 California | 53: 45 cones, 8 fences (`AZFENCE`, a striped barrier 1,100 wide) |
| 6 Switzerland | 22 cones |
| 2, 5, 7 | none (OSTACLES has no rows) |

- **Standing** (`0x30b29`). Each place of the list (a node's `+4`, `+8`; `+0xc` the row, whose first name is the mesh) is stood on the ground there: the height of the ground (`0x28ce6`, `track_ground_s2()`), the heading of the nearest road point (`0x2a371`), and the two angles that lay it on the ground face (the face's normal turned about the vertical by the heading less a quarter turn, each level part an angle): (pi, heading, pi) on level ground. The record is the spark's (`0x3c` bytes: the place x, height, z, three angles, three speeds, flying `+0x34`, knocked `+0x38`).
- **A car against them** (`0x2a639`, from the frame `0x2b9b1` after the race's frame, for every car whose height difference and x difference from the player's add up to under 20,000 -- the game leaves the z out -- and in time attack for the player's car alone). An obstacle within 200 of the car's height and 2,000 of its middle is knocked when the car's nose point (half the car's length on along the way it just went, swept from last step's place to this step's) passes within the car's reach of it (`|cos(wheels' angle)| x width + |sin| x length`). It flies off along the car's way turned by `((x + z) & 15) - 7` x 1.8 degrees (a chance from its place), up by the sine of the car's climb + 0.26, at **1.4 x 111 x the car's speed** (the record's `+0x500`). **The car is not touched**: the game counts the obstacles a car knocked in its record `+0xc88` and nothing reads the count (searched in the whole program), and the sound is sample `0x10` for the car the camera follows. So there is no effect on the car's motion to build.
- **Flying** (`0x2c475`, every frame). It falls (7,848 a second squared), moves by its speed and turns against it (0.0008, 0.0004, 0.00015 of the speed). With no face under it it meets the nearest wall if there is one (put back out of it, its speed turned about the wall by twice the angle between the wall and its way, half the cosine of that across, half up), else the ground is at its own height (`0x4cd64` = its height cut: below nought that is at once). At or under the ground it lands: 0.7 of each speed, the up speed turned upwards; under 300 it stops, and on the ground it leans with it as when it was stood up.
- **Sparks** (`0x2aeb9`). A touch (the solver `0x245a3`, `race.c`) or a wall knock (`0x29571`, `s2car.c`) throws `speed x 0.5` of them (30 at most; the speed is the knock's in units a second x 3600 / 400,000 x 30 / 60), from the place 100 up, into the first (touch: records 0 .. 29, mesh `AZTRI`) or second thirty (wall: 30 .. 59, `AZ1TRI`) of sixty records, over what still flies there; each flung with `rand() % 3000 - 1500 + 0.9 x direction` along and across (the touch: the mean of the two points' pushes; the wall: the direction's x is left 0, its z the push's), `1000 + rand() % 2000` up, three starting angles of `rand() % 500` x 0.01257 radians (up to a whole turn), two seconds to live; flown by `0x2cc70` as an obstacle without the ground. The game's `rand` is its C library's (`seed x 0x41c64e6d + 0x3039`, bits 16 to 30) started afresh with its 100 Hz counter at every call: here the counter is two a step, so the sparks are the race's function. The spark meshes are two small triangles back to back (28 x 24 units) of two flat colours of `MISC.MLB`.
- **Drawn.** The meshes are the track's graphics container's (`GFX/MAPnH01.DAT`: `AZCONE`, `AZFENCE`, `AZCHEST`, `AZCRATE`, `AZTRI`, `AZ1TRI`, 0.7 to 1.6 KB) read at the load as the scenery's are (`s2_mesh_load()`, faces moved onto the image's copy of `MISC.MLB`'s records: all plain colours (routine 16) but the fence's two textured boards (routine 64)); the object's angles are the game's record's, 2,048ths of a turn cut towards zero, as a car's (the pitch the game's negated). Each is a `track_object` after the effects (`s2props_objects()`), its block made when the drawing comes to it (`make`: the stored picture of a lying obstacle, its level of detail by the distance as a moving object's); the engine sorts it among the scenery as it does a car. The engine's list held 200 objects (`0x4bd1b`); the core's frame has room for **212** now (`TRACK_MAX_OBJS`: cars 4, shadows and puffs 68, scenery 16, obstacles 64, sparks 60: the drawing's lists grow by 928 bytes, the viewer's object list by 5.5 KB; the props' own state 6 KB, the meshes' buffer 8 KB: **25.2 KB of `.bss`** in all, in the program's SDRAM window), the props last, so that a frame over the limit would leave out props and not cars. An obstacle further than the track's far plane is not handed on (`track_far()`).
- **A race stays a function of the player's controls** (the replay and the ghost depend on it): the props only read the cars, and write the one record word `+0xc88`. `race.c` calls them at the end of every step (`race_step_hook`, `s2car_sparks`: null in the tools, so `check_replay_s2.sh`, `check_ghost_s2.sh`, `check_aicontact_s2.sh` do not link them), not once a frame, so what a late frame does changes nothing. A new race stands the obstacles up where the list has them (whatever became of them in the race before) and clears the sparks; `check_props_s2.sh model` runs a race twice and holds the props' whole state after every step equal.

## Simulation

Verilator runs in Docker (`verilator/verilator:v5.050`). Each testbench lives in
`sim/<name>/`: `files.f` names the top module and the sources, `tb.cpp` drives them.

```sh
# Two framebuffers: load two pictures from the game data over the bridge, swap them by key,
# capture 13 frames and check 12 of them pixel by pixel (one is interrupted by a reset).
python tools/make_screen.py "C:/GOG Games/Screamer/GFX/GRAF.DAT" LOAD2L.PCX \
    build/sim/screen.bin build/preview/LOAD2L.png
python tools/make_screen.py "C:/GOG Games/Screamer/GFX/GRAF.DAT" LOAD1L.PCX \
    build/sim/screen2.bin build/preview/LOAD1L.png
tools/sim.sh display build/sim/screen.bin build/sim/screen2.bin build/sim/display_frame

# The CPU system with firmware and a model of the SDRAM: self-tests, memory test, test band,
# log over the bridge, then two resets with reloaded firmware.
tools/fw.sh
tools/sim.sh soc build/firmware/firmware.bin build/sim/soc
# Fault test: an instruction fetch behind the boot RAM, the trap handler has to report it.
tools/fw.sh FAULT=IFETCH
tools/sim.sh soc build/firmware-IFETCH/firmware.bin build/sim/soc_ifetch 80 c0000001
# Counter-checks: one fault in a memory model at a time, the memory test must fail exactly
# the expected tests.
tools/sim_faults.sh

# Random test of the SDRAM port and controller against the SDRAM model: seed, clocks.
tools/sim.sh sdram 1 2000000
# Self-test of the SDRAM model: one correct and one wrong sequence per rule.
tools/sim.sh sdram_model
# The mixer (audio.v) against its C model firmware/mixer.c: random voices, loops, steps and
# volumes; every output value as it leaves over I2S is compared. Values, seed.
tools/sim.sh audio 20000 1
# The FM music (opl.v with the real JTOPL chip): the write queue's timing, the chip's pitch
# against the register values, the gain, run = 0.
tools/sim.sh opl
# A song on the real chip into a WAV file (events from tools/host/fmdump.c, "events"), to
# listen to and to measure the level: tools/sim.sh opl play <events> <seconds> <out.wav> [gain]
```

The SDRAM model in `sim/models/sdram_model.v` checks the datasheet timings in clocks and can be
built with injected faults for the counter-checks (`SIM_DEFINES`, see `tools/sim.sh`).

`tools/simcheck.sh [--full] [--save] [name]` runs the SoC simulation with the game files from
`build/gamedata/` (`SCREAMER2.zip`, which the testbench reads where the firmware asks, and small
`GAME.GOG` and `GAME.DAT`) and summarizes it in a few lines (`tools/simsum.py`). Without `--full` it
is the quick run (no resets); `--full` behaves like the Pocket. Without a track image (`SIM_IMAGE`) the
program stops at the files screen, so the check is its title bar and the log (`SCREAMER2.zip: ...`, `game
files: ...`, one line per file of the read test). With `SIM_IMAGE` the viewer runs (see above) and the
testbench only checks the log (the track's `T1 load ...` line), the picture is `build/sim/<name>.rgb`. The audio of the
run (I2S output, 48 kHz stereo) goes to `build/sim/audio.wav`.
